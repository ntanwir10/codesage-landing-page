CodeSage is a self-hosted tool. There is no hosted demo: you run the backend on your own machine or server, with your own Algolia account. Everything that does work runs inside one FastAPI process, unless you move indexing out to worker processes. The other parts are clients (the dashboard, the MCP bridge) or proxies (nginx) that talk to that process.

This page explains what each part is, why it was built that way, and what happens in order when the server starts, when a request arrives and when an MCP client calls a tool. For the numbers behind indexing, read [the indexing pipeline](/docs/concepts/indexing-pipeline/). For the index itself, read [search](/docs/concepts/search/).

    api -- "read files" --> db

The split of work follows one rule: Algolia answers questions about meaning (which function matches these words), and the database answers questions about exact content (give me lines 40 to 80 of this file). Searching goes to Algolia. Reading a file, listing definitions, analysing a repository and finding patterns go to the database. That is why every repository is stored twice: once as full file text in the database, once as small records in Algolia.

### Why the bridge is a separate process

An MCP client such as Claude Desktop, Cursor or VS Code starts stdio MCP servers as child processes and talks to them over stdin and stdout. The bridge is that child. It does not import the backend, open the database or hold an Algolia key. Two benefits follow:

- **The backend can run anywhere.** The bridge only needs a URL (`MCP_SERVER_URL`), so the backend can live on another machine behind nginx.
- **`tools/list` works with the backend down.** Tool names, argument models and result models live in [`backend/codesage_mcp/schemas.py`](https://github.com/ntanwir10/codesage-algolia-challenge/blob/master/backend/codesage_mcp/schemas.py), which the backend imports too. That file may not import app, database, Algolia or settings code, so it loads anywhere. Only tool calls and resource reads need the backend.

The bridge validates arguments first (unknown arguments are rejected), then the backend validates them again. Requests time out after 30 s, and a connection attempt after 5 s. A failed connection is retried once. stdout carries the protocol only, and all logging goes to stderr.

## Two entry points, one backend

There are two ways in, and both end at the same FastAPI backend.

- **Web dashboard.** You add a repository from GitHub or another git host, watch it index over a WebSocket (with 3-second polling as a fallback), and search it. The dashboard, `POST /api/v1/repositories/` and the `add_repository` tool take the same URLs.
- **MCP clients.** Claude Desktop, Cursor, VS Code, Windsurf and other clients call the eight tools through the bridge. Your assistant can also add public repositories from GitLab, Bitbucket and other git hosts with the `add_repository` tool.

Both entry points reach the same indexing service, so a repository added from your assistant shows up in the dashboard and the other way round.

### Middleware order

Starlette wraps middleware so that the last one added is the outermost. `main.py` adds them in this order, so a request meets them from the outside in:

1. **CORS.** Added last, so it is outermost. Because it wraps everything below it, even a `403` from the guard carries CORS headers that a browser can read.
2. **Request ID.** Reuses an incoming `X-Request-ID` or makes a new one, binds it to the log context and echoes it in the response.
3. **Request guard.** `BrowserRequestGuard` checks the `Host` and, for writes and WebSocket handshakes, the `Origin`. It was added first on purpose: the request-ID middleware wraps it, so the guard's `403` responses carry an `X-Request-ID` too. See [the security model](/docs/concepts/security/).
4. **Routes.** Per-route dependencies check the API key and the rate limiter.

The catch-all `500` handler is different. It sits in Starlette's outermost error layer, outside CORS. It adds the CORS headers itself for an allowed origin, so a browser can still read `{detail, request_id}` when something breaks.

## One tool call, step by step

<Mermaid caption="A tool call from your assistant to an answer. The key, origin and rate limit are checked before any data is touched." code={`sequenceDiagram
    actor You
    participant Claude as MCP client
    participant Bridge as MCP bridge
    participant API as Backend
    participant Data as Algolia or the database
    You->>Claude: ask a question
    Claude->>Bridge: tools/call
    Bridge->>API: POST /ai/mcp/tools/call
    Note over API: checks key,<br/>origin, rate limit
    API->>Data: query
    Data-->>API: matches
    API-->>Bridge: result or error
    Bridge-->>Claude: tool result
    Claude-->>You: answer with code
`} />

- **Bridge.** It checks the arguments with the same models the backend uses, refuses to send the key over plain `http://` to a remote host, and posts `{tool_name, arguments}` to `/api/v1/ai/mcp/tools/call`.
- **nginx (prod).** The request goes through nginx, which checks your login and adds the API key. The bridge sends a basic-auth login instead of a key in this case.
- **Backend.** The guard checks the `Host`. The route checks the key and the 30-per-minute limit. `search_code` queries Algolia. The other tools read the database. Every tool except `list_repositories` and `add_repository` refuses a repository that is not `completed`, and says why or how far along it is.
- **Errors.** A tool failure such as an unknown repository comes back as HTTP `200` with `is_error: true`, so the assistant sees the message. A rejected key (`401`), a refused host (`403`), a wrong URL (`404`), bad arguments (`422`), a rate limit (`429`), a backend error (`5xx`), a timeout or an unreachable backend all become a tool error that says what to fix. The full table is in [MCP endpoints and errors](/docs/reference/mcp-endpoints/).

## The request path: dev versus prod

The same backend sits behind three different front doors, depending on how you run it.

| | Local (`make start`) | Docker dev (`make up`) | Docker prod (`make prod-up`) |
| --- | --- | --- | --- |
| Dashboard served by | Vite dev server on `localhost:5173` | nginx on `127.0.0.1:80`, built bundle | nginx on 443, built bundle |
| Browser to API | Vite proxies `/api`, `/ws` and `/health` to `127.0.0.1:8001` | nginx proxies `/api/`, `/ws` and `/health` to `backend:8001` | nginx proxies `/api/` and `/ws` to `backend:8001`. `/health` is open |
| Where the API key comes from | `VITE_CODESAGE_API_KEY` in the bundle, copied from `backend/.env` | Same, baked in at build time | nginx adds `X-API-Key`. The bundle has no key |
| Login | none | none | basic auth in nginx |
| Bridge connects to | `http://127.0.0.1:8001` | `http://127.0.0.1:8001` | `https://your-host` through nginx |
| Backend reachable from outside | bound to `127.0.0.1` | published on `127.0.0.1:8001` only | not published at all |

<Mermaid caption="The production request path. Only nginx is published. The backend trusts the headers nginx sets because nothing else can reach it." code={`flowchart TB
    browser(["Browser"]) --> https["nginx :443<br/>HTTPS, basic auth"]
    https -- "static files" --> spa["Built dashboard"]
    https -- "/api and /ws<br/>adds X-API-Key" --> backend["backend :8001<br/>API_WORKERS uvicorn processes"]
    backend --> db[("SQLite volume")]
    backend --> algolia[("Algolia")]
    browser -. "plain HTTP" .-> http["nginx :80<br/>/health and a redirect"]
    http -. "/health" .-> backend
`} />

Why the two Docker stacks differ: in the dev stack the dashboard is a static bundle that has to authenticate itself, so the key goes into the bundle and the ports are limited to loopback. In the prod stack the human authenticates to nginx, and nginx authenticates to the backend. The browser never holds the key. The trade-off is that prod needs a certificate and a password file. The details are in [Docker dev stack](/docs/guides/docker/) and [Production deployment](/docs/guides/production/).

## Process model

The dev stack runs one uvicorn process. The prod image runs `API_WORKERS` of them (`--workers $API_WORKERS` in `backend/Dockerfile.prod`, 1 by default). Four things live in each process:

| State | Where it lives | With more than one API process |
| --- | --- | --- |
| Job table (`_jobs`) | A module-level dict of asyncio tasks in `repository_service.py` (inline mode) | Unused: more than one process requires `INDEX_WORKERS=external`, where the `jobs` table is the queue. Its unique index on `repository_id` lets only one process queue a repository |
| Run slots | An `asyncio.Semaphore(2)` per event loop | Unused for the same reason; each worker process runs one job at a time |
| WebSocket subscribers | `WebSocketManager` in `websocket_service.py` | Each process serves its own clients. With external workers every API process reads progress back from the database (`relay_progress`), so every client hears every run |
| Rate-limit counters | slowapi storage, memory by default | More than one process requires `RATE_LIMIT_STORAGE_URL=redis://…`, so every process counts in one place |

The backend refuses to start with `API_WORKERS` above 1 unless `INDEX_WORKERS=external` and `RATE_LIMIT_STORAGE_URL` are set. Processes starting together take turns applying the migrations, under a Postgres advisory lock or a lock file next to the SQLite database. SQLite allows one writer at a time: WAL mode lets readers work during a write, and the writers take turns. For heavy write load, or processes on more than one machine, use Postgres.

Indexing can move out with one API process too. With `INDEX_WORKERS=external`, the API only queues jobs in the `jobs` table, and any number of `python -m app.worker` processes claim them, one job at a time each, with a heartbeat. See [Configuration](/docs/reference/configuration/).

Inside each process, blocking work is moved off the event loop so the API, WebSocket and tool calls stay responsive while a repository indexes:

- Parsing runs in a worker thread (`asyncio.to_thread`).
- The Algolia client (v4 `SearchClientSync`) is synchronous, so each call runs in a worker thread too.
- Database commits for a batch and the bulk deletes of a run's old rows run in worker threads.
- `find_patterns` regex scans run in a thread with a per-file and a per-call time budget.

<Aside>
To run more than one API process, follow [More than one API process](/docs/guides/production/#more-than-one-api-process).
</Aside>

The prod image also starts uvicorn with `--forwarded-allow-ips "*"`. That makes uvicorn trust `X-Forwarded-For` and `X-Forwarded-Proto` from any peer. It is safe only because the backend has no published port and nginx overwrites both headers. If you ever publish the backend port, remove that flag.

## Start-up sequence

When uvicorn imports `app.main`, some work happens at import time and the rest in the FastAPI lifespan.

<Mermaid caption="What happens from process start to the first request. Settings errors stop the process; a missing Algolia key does not." code={`flowchart TD
    start(["uvicorn imports app.main"]) --> env["load_dotenv, build Settings<br/>configure JSON logging"]
    env --> engine["Create the SQLAlchemy engine<br/>no connection yet"]
    engine --> app["Create the FastAPI app,<br/>middleware, routes, /ws"]
    app --> life["Lifespan starts"]
    life --> validate{"validate_runtime_settings<br/>CORS has *? No key on a<br/>non-loopback host?"}
    validate -- "yes" --> stop["RuntimeError, process exits"]
    validate -- "no" --> migrate["upgrade_database<br/>stamp if pre-Alembic, then upgrade head"]
    migrate --> recover["recover_interrupted_jobs<br/>pending or processing runs again in full"]
    recover --> algolia{"Algolia credentials set?"}
    algolia -- "no" --> warn["Log an error and keep running<br/>health reports degraded"]
    algolia -- "yes" --> ready["Log ready"]
    warn --> serve(["Serve requests"])
    ready --> serve
`} />

1. **Settings.** `Settings` reads environment variables and `backend/.env`. An `ALGOLIA_APP_ID`, `ALGOLIA_ADMIN_API_KEY` or `GITHUB_TOKEN` that is empty or looks like `your-...-here` counts as unset.
2. **Logging.** structlog is set up once with a JSON renderer. Each line carries a timestamp, a level, the logger name and any bound context such as `request_id`.
3. **Settings validation.** `validate_runtime_settings` refuses to start when `CORS_ORIGINS` contains `*` (credentials are allowed, so a wildcard would be unsafe) or when `CODESAGE_API_KEY` is unset and `MCP_SERVER_HOST` is not a loopback address. With no key on loopback it logs a warning instead. With a key, an `ALLOWED_HOSTS` of `*` logs a warning.
4. **Migrations.** `upgrade_database` brings the schema to the latest Alembic revision. A database that has the app tables but no `alembic_version` table is stamped at `baseline` first. In-memory SQLite skips Alembic and is created from the models. See [the data model](/docs/concepts/data-model/).
5. **Crash recovery.** Jobs run inside the process by default, so a run left open by a previous process died with it. `recover_interrupted_jobs` starts every repository still `pending` or `processing` again as a full run. The previous index stays in place until that run completes. With external workers, a repository whose job row a worker owns is left alone: its job is queued again if that worker stops sending heartbeats for 5 minutes.
6. **Algolia check.** Missing credentials log an error but do not stop the server. `/health` then reports `degraded`, and adding a repository returns `503`.

`/health` runs a database `SELECT 1` and, at most once every 30 seconds, an Algolia `GET 1/indexes` request with a 5 s limit. A database failure gives `503 unhealthy`. Algolia down or not configured gives `200 degraded`, so a container health check stays green while you finish configuring Algolia.
